# 09. Тестирование

## Пирамида
1. **Unit-тесты** (больше всего): расчёты ЛУТ на Kotlin (`SheetCalculator`), проверки форм,
   нормализация телефона, OTP-хэш, JWT, обработка ответа синхронизации, ViewModel-логика.
2. **API-тесты backend**: каждый эндпоинт через `httpx.AsyncClient` и тестовую БД.
3. **Android-тесты сети**: Retrofit + MockWebServer (вход, `/sync`, пароль, refresh токена).
4. **Тесты Room** (DAO на настоящей SQLite в памяти) — instrumented, на эмуляторе.
5. **Ручная проверка** человеком по чек-листу ниже (после каждой фазы).

## Backend
- Тестовая БД: отдельная база `fuel_test` в том же контейнере PostgreSQL; перед каждым тестом —
  чистые таблицы (транзакция с откатом или truncate).
- SMS в тестах — только `FakeSmsSender`. Реальные запросы во внешние сервисы в тестах ЗАПРЕЩЕНЫ.
- Время — через инъекцию «часов» (`now()` как зависимость), чтобы тестировать истечение кода.
- Для каждого эндпоинта минимум: успешный сценарий, без токена (401), чужой ресурс (404),
  невалидные данные (400).
- Вход по паролю — обязательные тесты:
  хэш/проверка scrypt (верный, неверный пароль; хэш не равен паролю); `/auth/login` успех;
  неверный пароль, неизвестный номер, номер без пароля, `is_active=false` — все дают одинаковый
  401 `INVALID_CREDENTIALS`; 5 ошибок подряд → 429, и верный пароль во время блокировки → 429;
  после истечения блокировки (через инъекцию часов) вход снова работает; успешный вход обнуляет
  счётчик; лимит по IP; `is_new_user` зависит от пустого имени; CLI `set-password` создаёт
  пользователя/сбрасывает пароль и блокировку, `disable-password` выключает вход.
- `PUT /me/password` — обязательные тесты: первый пароль без текущего; смена с верным текущим;
  неверный текущий → 400 и попытка засчитана; блокировка → 429; длина 8..64; после смены
  `/auth/login` пускает с новым паролем и не пускает со старым.
- `POST /sync` — обязательные тесты: первая синхронизация (`cursor: null`) отдаёт всё; повторная с
  курсором — только новое; вставка и замена по id; удаление (и каскад на заправки листа);
  удаление несуществующего — не ошибка; чужой id → `rejected NOT_FOUND`, чужие данные не
  изменились и не видны; нет родителя → `PARENT_NOT_FOUND` (в т. ч. когда родитель отклонён в том
  же запросе); `SHEET_EXISTS`; неверное поле → `rejected VALIDATION_ERROR`, остальные записи
  приняты; имя профиля в обе стороны; больше 5000 записей → 400 и ничего не сохранено; 401.
- Запуск: `docker compose exec api pytest -q` · покрытие: `pytest --cov=app`.
- Цель покрытия: `services/` ≥ 90 %, в целом ≥ 75 %.

## Android
- `./gradlew test` — unit-тесты (JVM, быстро).
- `./gradlew connectedAndroidTest` — тесты на эмуляторе: DAO Room, UI ключевых экранов
  (вход, карточка ЛУТ).
- **Расчёты ЛУТ** — эталонные примеры A–I и все предупреждения из `06_BUSINESS_RULES.md`
  как unit-тесты `SheetCalculator`; проверки (валидации 1–11) и `next-prefill` — тоже unit-тесты.
- **Синхронизация** — unit-тесты с MockWebServer и фейковым хранилищем: отправляются только
  `is_dirty`; после успеха флаги сброшены, удалённые стёрты; запись, изменённая во время запроса,
  осталась `is_dirty`; пришедшие записи вставлены, `deleted` стёрты, локально изменённые не
  перезаписаны; `rejected` остались `is_dirty`; курсор сохраняется только после успеха; ошибка
  сети ничего не меняет; 401 → «Войдите снова»; вход другим номером при чужих данных — запрещён.
- ViewModel тестируются с фейковым репозиторием, без сети и без Room.
- Форматирование чисел/месяцев (`45,50 л`, «Октябрь 2026») — unit-тесты.

## Ручной чек-лист (сквозной сценарий)
1. Первый запуск → «Продолжить без входа» → имя → добавить авто «Lada Vesta», бак 50, норма 8,5.
2. Включить на эмуляторе режим полёта. Создать лист: пробег 52340, остаток 12; 2 заправки
   по 40 л × 55 ₽ → «Заправлено 80,00 л · 4 400,00 ₽», «Доступно 92,00 л».
3. Закрыть месяц: пробег 53340, факт. остаток 10 → итоги совпадают с примером A из `06_BUSINESS_RULES.md`.
4. «Новый лист» → подставились пробег 53340 и остаток 10,00. Перезапустить приложение — всё на месте.
5. Профиль (гость): нет синхронизации и «Выйти», есть «Войти и сохранить данные на сервере».
6. Выключить режим полёта. Войти: номер → код из логов backend (`docker compose logs -f api`) →
   «Загружаем ваши данные…» → в профиле «Последняя синхронизация: сейчас», «Не отправлено: 0».
7. Изменить заправку → «Не отправлено: 1» → «Синхронизировать» → «отправлено 1».
8. Задать пароль в профиле. Режим полёта → «Синхронизировать» → «Не удалось… Проверьте интернет»;
   «Выйти» → «Выйти не получилось…». Выключить режим полёта → «Выйти» → экран входа, данных нет.
9. «Войти по паролю» (номер + заданный пароль) → данные вернулись с сервера.
10. Второй эмулятор (или «Wipe data»): вход тем же номером → те же авто и ЛУТ.
11. Ввести неверный пароль 5 раз → «Слишком много попыток…»; верный пароль тоже не пускает до конца блокировки.
